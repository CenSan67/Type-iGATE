# iGATE Capstone Project (SKUL JUAN) - System Architecture & AI Guidelines

## 1. Safety Guardrails & Logic Preservation (Strict)
- **UI vs. Logic Isolation:** Never remove, refactor, or simplify existing state hooks (`useState`, `useEffect`), Firebase RTDB listeners, or business logic when performing UI/layout updates. Always preserve non-UI code line-for-line.
- **Strict Modification Constraint:** You are strictly forbidden from modifying state management, backend logic, or hardware handlers unless the prompt explicitly requests a logic change.

## 2. Architecture & Clean Code Rules (Anti-"Vibe Code")
- **Layered Architecture:** Keep UI components strictly for rendering layout. Abstract all Firebase operations and business logic into dedicated Custom Hooks (`/src/hooks`) or Service Classes (`/src/services`).
- **DRY Principle (Don't Repeat Yourself):** Avoid redundant inline code or duplicate UI elements. Reuse base components (e.g., Modals, Tables, Stat Cards) via generic props instead of creating single-use components.
- **Single Responsibility:** Each file must do ONE thing well. UI handles presentation; Hooks handle state/events; Services handle Firebase/hardware communications.

## 3. Communication & Code Quality Guidelines
- **Smarter & Direct Responses:** Skip unnecessary pleasantries or fluff. Provide concise explanations and direct, precise code edits.
- **Git Milestones:** Suggest clean git commits after achieving major, stable functional milestones.

# CLAUDE.md (Original Repository Context & Architecture)

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.


## What this is

iGate - a vehicle gate access & tracking system for Bulacan State University (Bustos Campus). React SPA (Vite) with Firebase (Auth + Realtime Database) as the backend. Staff log in and manage gate access logs, vehicle/account registration, payments, reports, and RFID-based entry/exit records.

## Commands

```bash
npm install     # install dependencies
npm run dev     # start Vite dev server
npm run build   # production build
npm run serve   # preview the production build
```

There is no lint script, no test runner, and no test files in this repo currently.

## Architecture

**Routing** (`src/App.jsx`): `react-router-dom` v6 nested routes, each top-level route rendering a `*Wrapper` component. `/login` is public; every other route is nested under `<RequireAuth />` (`src/components/auth/RequireAuth.jsx`), which redirects to `/login` if `AuthContext`'s `user` is null. `/account-management` and `/settings` are additionally nested under `<RequireRole allowedRoles={ADMIN_ROLES} />` (`src/components/auth/RequireRole.jsx`), which redirects non-admins to `/dashboard`. `ADMIN_ROLES` and the full `ROLES` list live in `src/constants/roles.js` — currently `Super Admin`, `Administrator`, `Security Guard` (no `Staff` login role; don't reintroduce it). `Sidebar` (`src/components/sidebar/Sidebar.jsx`) filters nav items by the same `roles` list so guarded pages aren't shown as dead links.

**Page composition pattern**: every feature folder under `src/components/` follows `Wrapper -> AppShell -> Page`:
- `FooWrapper.jsx` wraps `FooPage.jsx` in `AppShell` (see `src/components/dashboard/DashboardWrapper.jsx` for the canonical example).
- `AppShell` (`src/components/layout/AppShell.jsx`) renders the `Sidebar` plus a `<main>` content area, and reads/writes sidebar-open state via `AppStateContext`.
- Follow this same three-file pattern when adding a new top-level route.

**Global state** — two small context providers wrap the whole app in `App.jsx`:
- `AuthContext` (`src/context/AuthContext.jsx`): subscribes to Firebase `onAuthStateChanged`, then subscribes to `adminProfiles/{uid}` for the signed-in user's `role`, exposing `{ user, role, loading }` via `useAuth()`. `loading` stays true until both the auth state *and* the role fetch have resolved, so route guards don't flash the wrong content mid-login.
- `AppStateContext` (`src/context/AppStateContext.jsx`): a single `useReducer` for cross-cutting UI state — `sidebarOpen` and `activeModal` (`{ type, ...payload }`). Some modals (Payment's `RegistrationModal`, `RemarkModal`) are opened via `dispatch({ type: 'OPEN_MODAL', ... })` and rendered off `state.activeModal?.type` — prefer this for anything cross-cutting. In practice it's not universal: `RegisterRfidModal` (Dashboard), and `EditRfidUserModal`/`ConfirmModal` (Account Management) use plain local `useState` instead, since they're single-page-scoped and don't need to be reachable from elsewhere. Match whichever pattern the modal you're touching already uses rather than assuming one is canonical.

**Firebase** (`src/services/firebase.js`): initializes the v9 modular SDK and exports `auth` (Firebase Auth) and `rtdb` (Realtime Database — **not** Firestore; there is no `getFirestore()` call anywhere in this app). Config is currently hardcoded inline (not in an untracked `.env`, even though `.env` is gitignored) — do not add secrets beyond what's already there without checking with the user first. `src/services/auth.js` wraps `signInWithEmailAndPassword`/`signOut`.

**Data is live, backed by the Realtime Database.** Every top-level page (dashboard, payment, search-history, accounts, reports, settings) subscribes to `firebase.js` listeners (`listenToGateLogs`, `listenToRfidUsers`, `listenToPayments`, `listenToAdminProfile`) or the `useEnrichedGateLogs`/`useRfidScanner` hooks — none of them render hardcoded sample arrays anymore. RTDB paths in use: `gateLogs` (RFID scans), `rfidUsers` (registered vehicles/owners), `payments`, `adminProfiles/{uid}` (per-admin profile, keyed by Firebase Auth uid), `settings/app`, `users/system`.

`ProfilePage` falls back to a `localStorage` copy (`igate_admin_profile`) only when there is no authenticated `user` — every real login persists to `adminProfiles/{uid}` in RTDB instead, and the email field becomes read-only in that case since changing it here wouldn't actually update Firebase Auth.

`SettingsPage`'s "Recent Logs" panel merges real RTDB gate-scan history (via `useEnrichedGateLogs`) with locally-generated session events (gate toggle clicks, login) — the gate open/close buttons themselves are still local-only UI state, not wired to any hardware/RTDB command path.

There is no Firestore usage anywhere in this app. RTDB security rules **are** version-controlled: `database.rules.json` (repo root) is the source of truth, deployed to the Firebase console's Rules tab — `firebase.json` points the Firebase CLI at it for `firebase deploy --only database`. Rules require `auth != null` on every path, scope `adminProfiles/{uid}` to its own owner, and structurally validate writes to match the shapes in `src/models/`. Changing a write shape in `src/services/firebase.js` without updating both the matching `src/models/*.js` validator and `database.rules.json` will make writes fail silently against real rules even though local dev (which uses the same rules) may still pass if you haven't deployed the latest rules yet.

**Data models** (`src/models/*.js`): one file per RTDB entity (`gateLog`, `rfidUser`, `payment`, `adminProfile`, `appSettings`, `systemUser`), each exporting a JSDoc `@typedef` and a `validate*()` function that normalizes and throws on invalid shape. Every write in `src/services/firebase.js` runs its payload through the matching validator before `set()`/`push()`. This is plain-JS runtime validation, not TypeScript — the repo has no TS toolchain, don't introduce one for this without asking. `rfidUser`'s `role` field (Student/Faculty/Staff/Visitor — the vehicle owner's category) is unrelated to the admin login `role` in `src/constants/roles.js`; don't conflate the two. `rfidUser` also has `email` (optional, format-checked) and `status` (`Active`/`Inactive`, default `Active`) — format/enum patterns live in `src/utils/validators.js` (`isValidRfid`, `isValidPlate`, `isValidEmail`) and are shared between the model validators and every registration/edit form's inline field checks, so the two never drift apart.

**RFID user CRUD** (`src/services/firebase.js`): `registerRfidUser` (strict-create, throws on duplicate RFID — used by the Dashboard's "Register RFID" button) and `upsertRfidUser` (create-or-renew, never throws on an existing RFID — used by the Payment registration/renewal flow) are both open to any authenticated role, since Security Guards legitimately create/renew via those two entry points. `updateRfidUser` (full-field edit, Account Management's Edit modal), `deleteRfidUser`, and `setRfidUserStatus` (deactivate/reactivate) are the three actions gated to `ADMIN_ROLES` — enforced at the route level (`/account-management` is already admin-only) *and*, for delete/status specifically, at the RTDB rules level too (see below), because those two are meaningfully distinguishable from a guard's create/renew at the rules layer in a way a generic "edit" isn't.

**Why `database.rules.json`'s `rfidUsers` write rule looks the way it does**: RTDB rules see only the resulting data diff, not which UI screen or business operation produced it — so "Account Management edit" and "Payment renewal" are indistinguishable from the rules' point of view when both do a `set()` on an existing record. The rule therefore allows any authenticated role to create-or-update a record (`newData.exists()`), but requires `Super Admin`/`Administrator` when the write is a delete (`!newData.exists()`). The `status` child has its own `.validate` requiring the value be unchanged (fine for a guard's renewal `set()`, which resends the same status) or the actor already be an admin — this is what actually makes deactivate/reactivate admin-only, since the outer `.write` rule alone can't express it. If you touch this rule, keep both branches in mind or you'll either lock guards out of registration or let them silently deactivate accounts.

**Hardware note**: the physical RFID reader (`sketch_scanner.ino`, ESP32) POSTs directly to `gateLogs` over the RTDB REST API using a legacy database secret (`FIREBASE_AUTH` in the sketch), not Firebase Auth — a valid secret bypasses `database.rules.json` entirely, so the `auth != null` rule on `gateLogs` does not affect it. If `FIREBASE_AUTH` is ever blank in the sketch, the scanner depends on the rules being fully public and will silently stop logging scans the moment `database.rules.json` is deployed. A raw `gateLogs` entry only ever has `cardId`/`cardHex`/`direction`/`timestamp` (that's all the hardware knows) — never assume it carries `name`/`plateNumber`/etc. directly; always go through `useEnrichedGateLogs` (`src/hooks/useEnrichedGateLogs.js`), which joins each scan against `rfidUsers` by normalized `cardId`/`cardHex`, to get those fields.

**Live dashboard metrics** (`src/hooks/useGateStats.js`): computes `totalRegisteredVehicles` (active `rfidUsers` count), `vehiclesInsideCampus`, `todaysEntries`, `todaysExits` from the full `gateLogs` + `rfidUsers` listeners — rendered by `StatsCards`. "Inside campus" requires finding each card's single most recent scan across the *entire* history (a `Map` keyed by normalized `cardId`/`cardHex`, keeping whichever entry has the latest `timestamp`), so it can't be derived from a single new event — that's why this hook uses the full-history `listenToGateLogs` (`onValue`), not the event-stream one below.

**Hardware-ready live feed** (`listenToNewGateLogs` in `src/services/firebase.js`): uses RTDB's `onChildAdded` instead of `onValue` — the same event type a real ESP32 write triggers — filtered to entries timestamped after the listener attached (so the initial backlog burst `onChildAdded` always sends on mount isn't treated as "new"). Currently drives the "just scanned" row flash in `RecentActivityTable` and the "last scan received" live timestamp on `DashboardPage`; reach for this (not `listenToGateLogs`) for anything that should react to a single new scan as it happens rather than the whole list.

**Simulating hardware without physical scanner present**: `SimulateScanModal` (`src/components/dashboard/SimulateScanModal.jsx`, admin-only, triggered from `DashboardPage`) calls `logGateEntry` — the exact same function/validation path (`validateGateLog`) a real hardware-authenticated write would eventually reuse if the ESP32 ever posts through the app instead of raw REST. Useful for exercising the live dashboard/stats during development.

**Remarks feature**: `useRemarks(entries)` (`src/hooks/useRemarks.js`) stores **visit-scoped, per-person** remarks in `localStorage` (key `igate_visit_remarks`, `{ [rfidUsers record id]: { text, at } }`; `remarkKeyOf(row)` falls back to `card:<rfidId>` for a scan with no known holder). A remark lasts for the person's current visit: it stays through their OUT and is cleared by their **next IN** (`remarkFor` returns null once any IN is newer than the remark; `entryHasRemark` ticks only rows from the remarked visit's IN onward). The Dashboard's `RecentActivityTable` and `SearchHistoryPage` (keyed by `person.id`) share it, so a remark written on the Dashboard shows on that person in Search History. The older per-row/per-card keys (`igate_user_remarks`) are no longer read. UI: `RemarkModal` + `RemarkAddButton`/`RemarkTick` (`src/components/shared/RemarkBadge.jsx`). Search History's per-person scan table pages 4 rows at a time (`PERSON_LOG_PAGE_SIZE`) via the shared `PaginationRow` component.

**`SearchHistoryPage.jsx` has two independent sections**: the original single-person lookup (search by Plate/RFID/Name → one matched `rfidUsers` record + their own scan history) is unchanged, and a second "All Entry & Exit Logs" section below it is a general filterable/sortable/paginated table over every `useEnrichedGateLogs()` entry (date range, vehicle type, RFID, driver name filters; click `Time`/`Name` headers to sort; CSV via `src/utils/csv.js#downloadCsv` — no library, a hand-rolled `Blob` download — and PDF via `window.print()`, matching the same pattern `PaymentPage`/`ReportsPage` already use). `ReportsPage.jsx` has a similar-looking filter/table of its own that predates this — the two overlap in purpose but haven't been consolidated; don't assume one supersedes the other without asking.

**Barrier gate control** (`src/components/dashboard/GateStatusCard.jsx`, Phase 6): shows a live OPEN/CLOSED/UNKNOWN badge for the physical gate and, for any of the three staff roles (`ROLES`, not `ADMIN_ROLES` — Security Guards need this too, and it's on the Dashboard rather than System Settings specifically because `/settings` is admin-only), a manual override button (reusing `GateButton`, the same component `SettingsPage`'s local-only toggle uses) that goes through a `ConfirmModal` before writing. State lives at `settings/app/gateStatus` (`{ state, updatedAt, updatedBy, updatedByName }`, `src/models/appSettings.js#validateGateStatus`), written via `setGateStatus`/read via `listenToGateStatus` in `services/firebase.js` — always as a targeted leaf write, never through `validateAppSettings`/`initializeFirebaseCollections`, so a gate toggle can never clobber `appName`/`campus`/etc., and the once-per-app-mount `initializeFirebaseCollections()` call can never stomp a live gate state back to a default. A physical ESP32 relay controller is expected to read (and eventually write) this same path the way `sketch_scanner.ino` already reads/writes `gateLogs` today — over the RTDB REST API using a legacy database secret that bypasses `database.rules.json` entirely (see the hardware note below) — so no relay firmware exists in this repo yet and no rule was added to make the node publicly readable; `database.rules.json` only adds a `.validate` on `gateStatus` for shape (`state` must be `OPEN`/`CLOSED`, `updatedAt` a number).

**Visitor management & SMS alerts** (Phase 7): `rfidUser` (`src/models/rfidUser.js`) gained four fields, all optional: `phone` (canonical `09XXXXXXXXX`, normalized/validated by `normalizePhone`/`isValidPhone` in `src/utils/validators.js`), `expiresAt` (ms epoch, visitor-pass expiry), `hostName`, `purpose` (visitor-only, who/why). Visitors are **not** a separate RTDB node — they're `rfidUsers` with `role: 'Visitor'`, so they show up in every existing table (Dashboard, Search History, Account Management) for free; nothing auto-deactivates a record once `expiresAt` passes, that's advisory only today. `RegisterRfidModal.jsx` (Dashboard, guard-reachable) conditionally shows Host Name/Purpose/"Pass Valid For" fields and swaps its title/submit label to "Register Visitor Pass"/"Issue Visitor Pass" when `role === 'Visitor'` is selected — this is also where `expiresAt` gets computed from the chosen duration. `EditRfidUserModal.jsx` (Account Management, admin-only) also gained a `phone` field so existing records can be corrected. `.modal-card` picked up `max-height: 90vh; overflow-y: auto` here too — the visitor fields made this modal tall enough to overflow a fixed-position backdrop with no scroll, which would have made the submit button unreachable on shorter viewports; this fix applies to every modal built on `.modal-backdrop`/`.modal-overlay` + `.modal-card`, not just this one.

SMS is sent by a new Cloud Function, `functions/index.js` (`sendGateScanSms`, an `onValueCreated` trigger on `/gateLogs/{logId}`) — **not** from client code, because the Semaphore API key must never ship in the JS bundle. It re-derives the same cardId/cardHex → `rfidUsers` match as `src/hooks/useEnrichedGateLogs.js` (hand-copied, not imported — `functions/` is a separate Node package/runtime with no bundler linking the two; keep both in sync by hand if the match logic ever changes), and if the matched owner has a `phone`, POSTs to Semaphore's `v4/messages` endpoint and writes an audit record to `smsLogs/{logId}` (`database.rules.json`: client `.read` only, no client `.write` — the Admin SDK write bypasses that the same way the ESP32's legacy database secret bypasses rules for `gateLogs`, see the hardware note above). Fires on both IN and OUT scans. The Semaphore API key is a Cloud Functions **secret** (`defineSecret('SEMAPHORE_API_KEY')` from `firebase-functions/params`, bound via the trigger's `secrets:` option) — set once via `firebase functions:secrets:set SEMAPHORE_API_KEY` (run by a human, never through chat/AI tooling), not `functions.config()` (deprecated) and not a plain env var. `SEMAPHORE_SENDER_NAME` is a non-secret `defineString` param (default `SEMAPHORE`, overridable via `functions/.env`, see `functions/.env.example`). Deploying `sendGateScanSms` requires the Blaze (pay-as-you-go) plan — Semaphore is a non-Google outbound HTTP call, which the free Spark plan blocks entirely regardless of secrets being configured. As of this writing no Semaphore account/API key has been provisioned yet, so this function is written and installs cleanly (`node --check` passes, `npm install` in `functions/` succeeds) but has never actually been deployed or sent a real SMS — do that only after the secret is set. **UniSMS test provider**: setting `SMS_PROVIDER=unisms` in `functions/.env` makes `sendGateScanSms` send through UniSMS (`POST https://unismsapi.com/api/sms`, Basic auth with secret `UNISMS_API_KEY`, sender `UNISMS_SENDER_ID`, default `UniSMS` = Globe/DITO only until an own sender ID is approved) instead of Semaphore. It's read from `process.env` (not `defineString`) because it also picks which secret the trigger binds, and binding a never-set secret fails the deploy. `smsLogs` entries carry `provider`; the response is still stored under `semaphoreResponse`.

**`StatsCards.jsx`** was rebuilt in Phase 4 to show exactly `Total Registered Vehicles` / `Vehicles Inside Campus` / `Today's Entries` / `Today's Exits` (via `useGateStats`), replacing an earlier Car/Students/Faculty/Motorcycles/Total breakdown sourced from `rfidUsers`. That breakdown is gone, not hidden — if it's still wanted, it needs to be re-added as a separate component rather than assumed to still exist.

**RBAC audit & RTDB hardening** (Phase 9): `RequireAuth`/`RequireRole` (`src/components/auth/`) and the `/dashboard`, `/search-history`, `/reports`, `/payment`, `/profile` (any authenticated role) vs `/account-management`, `/settings` (`ADMIN_ROLES` only) route split in `App.jsx` were audited and found already correct — not rebuilt, per this project's own strict-modification rule. What the audit actually found and fixed was at the **RTDB rules layer**, since `RequireRole` is a UX convenience, not the real security boundary — the real boundary is `database.rules.json`, and several existing rules were more permissive than the frontend's own intent:
- `rfidUsers/{id}/rfidId` (which physical card a record is bound to) can now only be *changed* by an admin once a record exists — any authenticated role can still set it on first create (registration). Previously any authenticated role could silently reassign an existing record to a different card via direct Firebase access, even though no guard-facing flow ever does that (registration is create-only; renewal is looked up *by* rfidId).
- `gateLogs/{id}` and `payments/{id}` are now effectively **append-only** for non-admins: creating a new entry is unrestricted (matches how the ESP32/`SimulateScanModal`/`recordPayment` already only ever `push()` new entries), but modifying or deleting an *existing* entry is admin-only. `gateLogs`' `imageUrl` child is the one exception (still freely settable by any authenticated role, unchanged — `uploadVehicleSnapshot` needs this). Previously any authenticated role could silently rewrite or delete gate-log/payment history via direct Firebase access, which nothing in the frontend ever does or needs to do.
- `settings/app` (`appName`/`campus`/`status`/`createdAt`) is now Super Admin/Administrator-only to write, **except** `settings/app/gateStatus`, which deliberately keeps `"auth != null"` — Phase 6 intentionally lets Security Guards trigger the manual barrier-gate override from the Dashboard, and this phase must not break that. The child's own more-permissive `.write` rule works via RTDB's cascading semantics (a deeper rule can grant access a shallower one denies) — see the inline comments in `database.rules.json` and `firebase.js#setGateStatus` for how these two rules coexist.
- `App.jsx`'s `initializeFirebaseCollections()` bootstrap call is now gated to `ADMIN_ROLES` only (previously ran for every authenticated user on every mount) — a direct consequence of the `settings/app` change above, since a Security Guard would otherwise get a harmless-but-noisy `permission-denied` console error on every login.

`scripts/verify-firebase.mjs` was extended to be **role-aware**: it reads the signed-in test account's own role back from `adminProfiles/{uid}` and picks `expectAllowed`/`expectDenied` per admin-gated check based on that, so the exact same script correctly validates either direction depending on which account's credentials it's run with — run it once with a Security Guard account and once with an Administrator/Super Admin account to fully exercise the RBAC boundary. (No credential was ever entered by the assistant to do this — that's a deliberate, standing constraint: passwords are never handled in chat/AI tooling, even for test accounts.)

**Offline RFID authorization cache** (Phase 9, firmware): lives in the *sibling* `sketch_scanner` repo (`c:\Users\Cener\OneDrive\Documents\CAPISTON\SKUL JUAN\sketch_scanner\sketch_scanner.ino`), not this one — flagged here because it's tightly coupled to this repo's schema. Extends the Phase 8 offline-buffering ESP32 firmware with a local, LittleFS-cached snapshot of `rfidUsers` (`rfidId`/`status`/`plateNumber`/`vehicleType` only — task constraint was "don't store unnecessary Firebase data"), refreshed every 5 minutes while online via the same legacy-secret REST pattern the sketch already uses for `gateLogs`. When offline (or a live POST fails despite Wi-Fi being connected), a scan is checked against this cache before being buffered: authorized (registered + Active) → buffered to `/buffer.jsonl` with `plateNumber`/`vehicleType` now embedded on the JSON line (`gateLogs` has no rule restricting extra fields, so this is additive/inert to everything already reading that node); unauthorized (inactive, unknown, or no cache loaded yet) → denied and Serial-logged only, never buffered — per the user-supplied flowchart, "Deny Access" is a terminal state with no path to the buffer. A sync only ever replaces the on-disk/in-memory cache after a *fully successful* fetch+parse; any failure leaves the last-known-good cache untouched, so a bad network moment can never leave the gate with zero authorization data. Requires a new Library Manager dependency, **ArduinoJson v7** (not bundled with the ESP32 core) — parsing arbitrary incoming Firebase JSON by hand, unlike Phase 8's buffer lines which the sketch fully controls the shape of itself, was judged too risky for a security-relevant authorization decision.

**Payment, fees & document verification** (Phase 10): the Payment page's `RegistrationModal` (opened via `AppStateContext`, wide two-column layout with a live receipt panel) is the one registration path for Student/Faculty/Staff; the Dashboard's `RegisterRfidModal` is now **visitor-only** (temporary pass, visitor leaves a valid ID at the guardhouse) so nothing can be registered without paying, verification and consent. Pricing lives in `src/constants/fees.js` (`VEHICLE_FEES`: Motorcycle 50, Tricycle 75, Car/Truck 100 - large EVs register as Car; E-Bike/E-Scooter 50 is a placeholder; same fee for Registration and Renewal), together with `REGISTRATION_VALIDITY_MONTHS` (5, **unconfirmed by the university** - change only there), the per-vehicle-type required documents (`license`+`orcr` for motor vehicles, `validId` for e-bike/e-scooter, plate optional for those two), and the privacy-consent text/version. Documents are **verify-only**: the guard ticks that the originals were checked (+ license expiry date, expired = blocked); nothing is scanned or uploaded, so there are no document images to protect - what's recorded, on the append-only `payments/{id}`, is `docsVerified`, `licenseExpiry`, `consentAt`, `privacyNoticeVersion`, `receivedBy`/`receivedByName`, `amountTendered`/`change` (`amount` stays the fee charged, which "Total Collected" sums) and a sequential `receiptNo` from a transaction on `counters/receipt` (`getNextReceiptNo`; a failed payment write after it leaves a gap, never a duplicate). `database.rules.json` forces `receivedBy === auth.uid` on create, `amountTendered >= amount`, and `counters/receipt` may only increment by 1 - **these rules must be deployed** (`firebase deploy --only database`) or registration fails on the counter write. Fees ARE enforced by the rules now (a new `payments` entry must charge exactly `VEHICLE_FEES[vehicleType]`, hand-copied into `database.rules.json`), so changing a fee in `fees.js` needs the same change in the rules + `firebase deploy --only database`. The write sequence lives in `hooks/usePaymentRegistration.js` (next receipt no -> `upsertRfidUser(fields, { payment })`, which writes the `rfidUsers` record and its `payments/{id}` in ONE atomic multi-path `update()`, the record carrying `paymentId`); `ReceiptModal`/`ReceiptSummary` render the receipt and share `PrintPreviewFrame` with `PrintReportModal`. `rfidUser` gained optional `vehicleColor`; `VEHICLE_TYPES` gained `Tricycle` and `E-Scooter`.

**VIP pre-clearance & visitor pass return** (Phase 11): a new `expectedGuests/{id}` node (`src/models/expectedGuest.js`) lets an Administrator pre-clear a guest (`VipGuestsPanel`, Account Management: name, category — `Guest Speaker`/`University Dignitary`/`Government Official`/`VIP Event` — host, optional purpose/plate, an arrival window) so they never queue or hand over an ID at the gate. A guard checks them in/out from the Dashboard's `GuestClearancePanel` (visible to all three roles, same as the rest of the Dashboard) without needing an admin: **Check In** (`checkInGuest`) scans a temporary card and issues it as an ordinary `rfidUsers` record with `role: 'Visitor'`, `expiresAt` = the guest's `validUntil`, `hostName`/`purpose` carrying the category — the exact same shape a walk-in visitor pass already has, so it shows up everywhere those do — then flips the guest to `Arrived`; **Check Out** (`checkOutGuest`) deactivates that pass and flips the guest to `Departed`. No payment is recorded - VIP guests don't pay the registration fee. `database.rules.json`'s `expectedGuests` rule gives admins full read/write always, and gives every other active role exactly one thing: flipping `status` `Expected`/`Arrived` -> `Arrived`/`Departed` while every other field (`name`/`category`/`hostName`/`purpose`/`validFrom`/`validUntil`/`createdBy`) stays byte-for-byte the same - a guard can never create, delete, cancel, or edit a guest's core details, only advance it through the gate. Walk-in (non-VIP) visitor passes get the same one-way self-service return: `rfidUsers/{id}/status`'s `.validate` now also allows any active role to set it to `Inactive` (never back to `Active`) when the record's own `role` is `Visitor`, so a guard can return a pass from the Dashboard's `VisitorPassesPanel` (`setRfidUserStatus`, already existed) without admin help. `useVisitorPasses` excludes any `rfidId` that an `expectedGuests` entry claims, so a checked-in VIP's pass shows only in `GuestClearancePanel`, never doubled up in `VisitorPassesPanel`. Both Dashboard panels render nothing when there's nothing to act on (no empty-table clutter). No new CSS - both panels and both new modals (`AddExpectedGuestModal`, `CheckInGuestModal`) reuse `.activity-panel`/`.activity-table`/`.registration-form`/`.rfid-scan-row` etc. **This phase's `expectedGuests` rule must be deployed** (`firebase deploy --only database`, same deploy as Phase 10) before pre-clearance works at all.

**Temporary pass lifecycle - pooled cards** (Phase 12): visitor/VIP passes reuse a small pool of physical cards, so one `rfidId` has many `rfidUsers` records over time. Flow: register (Dashboard visitor form / VIP Check In) creates an Active record and sends a `SYNC` scanner command - it does **not** log an IN or move any barrier anymore; the visitor's own card scan at the gate opens the entry barrier and logs the IN (`esp32-live`). Exit is either (a) the card's OUT scan - `sketch_scanner.ino#autoReturnVisitorPass` logs the OUT, then PATCHes `rfidUsers/{key}` to `status: Inactive` + `returnedAt` = the OUT's timestamp (and, for a VIP pass carrying `guestId`, `expectedGuests/{guestId}` to Departed), queueing to `/returns.jsonl` when offline - or (b) Return Pass / VIP Check Out in the app (`services/firebase.js#returnTemporaryPass`: OUT logged only if the card's last scan is IN, then Inactive + `returnedAt`, then an `EXIT` command that opens the exit barrier). `returnedAt` is what "wipes" the card: `src/utils/cardHolder.js` is the ONE place that answers "who is this card" (`holderAtTime` for a scan, `currentHolder`/`renewableRecord` for now) and never attributes a scan after `returnedAt` to that visitor; a returned pass is never loaded into the Payment form or overwritten by `upsertRfidUser`. Every card->person lookup (`useEnrichedGateLogs`, `useGateExitNotifications`, `RegistrationModal`, `upsertRfidUser`, `checkOutGuest`, Search History's per-record log filter) goes through it - don't reintroduce a bare `users.find(u => u.rfidId === ...)`. `functions/index.js#findOwnerByCard` is a hand copy of `holderAtTime`. Records are kept (Inactive), not deleted, so past visits keep their names in logs/reports.

**Scanner commands** (`devices/scanner/command`, `sendScannerCommand`): `{ id, action: 'EXIT'|'SYNC'|'OPEN_ENTRY'|'OPEN_EXIT'|'OPEN_BOTH'|'CLOSE_ENTRY'|'CLOSE_EXIT'|'CLOSE_BOTH', cardId, requestedAt, requestedBy, requestedByName }`, writable by any Active staff (`requestedBy` must equal `auth.uid`). The `OPEN_*` actions are Gate Control's Open buttons (`GateStatusCard`: Entrance, Exit, and Both Gates - both motors at the same time). `settings/app/gateStatus` is written ONLY by the ESP32 (OPEN when it starts the motor, CLOSED when the run ends) - the app never marks a gate OPEN itself (it used to, and the badge stuck OPEN whenever the scanner didn't run the command). The card waits for `devices/scanner/commandAck` with its command id (10 s timeout -> "gate controller did not respond"), then locks every Open button for `GATE_BUTTON_LOCK_MS` (motor run `GATE_MOTOR_RUN_MS` = the sketch's `MOTOR_RUN_TIME`, + 1 s). Every command is acked, including ones skipped as stale after a reboot (a command waiting at boot runs only if sent within the last 15 s). Open = motor forward (LPWM) for `MOTOR_RUN_TIME`, Close = the same motor in reverse (RPWM) for `MOTOR_CLOSE_TIME` (open - 200 ms; mirrored in the web app as `GATE_MOTOR_RUN_MS`/`GATE_MOTOR_CLOSE_MS` for the button lock); **closing is manual only** - a barrier opened by a card scan, Return Pass or Gate Control stays open until Close is pressed (or `close <gate>` in the Serial tester). The ESP32 remembers each barrier's state in `/gates.json` (`moveGates`), only moves a barrier whose state changes (a scan at an already-open gate logs but doesn't drive the motor; acks "already open"/"already closed"), and publishes every change plus its state at boot to `settings/app/gateStatus` - the buttons show Open or Close from that. If the remembered state is ever wrong (barrier moved by hand), fix it with the tester's `gatestate <entry|exit> <open|closed>`. Firmware: each motor run is ended by a one-shot `esp_timer` (`armMotorStopTimer`), not by `loop()` - the blocking network calls after a scan (gateLogs POST, camera trigger, cache sync) used to stretch a 0.8 s run to several seconds. The ESP32 polls it every 1.5 s over a kept-alive TLS connection, runs each new `id` once, acks to `devices/scanner/commandAck`, and ignores whatever command is already waiting when it boots (a stale EXIT can never fire after a restart). Best-effort: an offline scanner just misses it. Firmware side also: the authorization cache stores each card's current record `key`/`role`/`guestId`, and the IN/OUT memory is per registration (`directions.json` stores `{in, key}`), so a reissued card always starts at ENTRY for its new holder. Requires `firebase deploy --only database` (command rule + `returnedAt`/`guestId` validation).

**Device status & auto-close setting**: the scanner and the ESP32-CAM each PATCH a heartbeat `lastSeen` (Firebase server time, `{".sv":"timestamp"}`) to `devices/scanner` / `devices/camera` every ~30 s; `hooks/useDeviceStatus.js` calls a device Offline after 75 s without one (compared against `.info/serverTimeOffset`), and the Dashboard's `ScannerStatusBadge` shows Scanner Ready/Warming Up/Offline + Camera Online/Offline. "Ready" alone can't detect a disconnected board (written once at boot), and the UHF reader itself is a passive Wiegand device - the ESP32 cannot tell whether it is plugged in. Barrier auto-close (scan / Return Pass) is timed by an `esp_timer` (`autoCloseTimerCallback`, 100 ms), not `loop()`, because `loop()` blocks for up to ~13 s on the gateLogs POST + camera trigger; its delay (default 4 s) is set from the Dashboard by admins (`AutoCloseControl` -> `SET_AUTO_CLOSE` command with `seconds` 1-60, saved on the board in `/settings.json`, reported back as `devices/scanner/autoCloseSeconds`). VIP guests still `Expected` can be rescheduled (`updateExpectedGuestWindow`, `EditGuestWindowModal`) or cancelled by admins from either guest panel via the shared `GuestAdminActions`.

**Offline behaviour**: the gate never needs the internet to let a registered car through - the ESP32 decides from its LittleFS card cache, buffers authorized scans to `/buffer.jsonl` (and visitor-pass returns to `/returns.jsonl`) and uploads them oldest-first when Wi-Fi is back; buffered scans carry no camera photo. It has no battery clock, so it saves the real time to `/clock.txt` every 5 min and, after an offline boot, estimates from that; lines queued with an estimated time carry `boot`/`ms` and are corrected to the exact time on upload if NTP answers during the same boot (`resolveQueuedTime`), otherwise uploaded with `timeApprox: true`. Web side: `hooks/useConnectionStatus.js` (`.info/connected`, 4 s grace) drives `shared/ConnectionBanner` in `AppShell` and disables Gate Control / auto-close Save; `services/firebase.js#assertOnline` makes scanner commands, Return Pass, guest check-in/out and payment registration fail at once offline instead of being queued by the SDK. A command's `requestedAt` is Firebase server time, and both `database.rules.json` and the scanner refuse one older than 60 s, so a queued command can never move a barrier later.

**Vehicle brand** (`rfidUsers/{id}/vehicleBrand`, optional): CAPS make ("TOYOTA", "MERCEDES-BENZ"), a custom brand typed under "Other", or "NO VEHICLE"; absent on records saved before it existed, displayed as "Not specified" - never defaulted. All rules live in `src/constants/vehicleBrands.js` (list, `resolveVehicleBrand` form -> stored value + errors, `vehicleBrandFormValue` stored -> form, `formatVehicleBrand`); `models/rfidUser.js` normalizes/validates and only writes it when set; `database.rules.json` validates string 2-40 chars. Entered through `shared/VehicleBrandField` (on top of the generic `shared/SearchableSelect`) in Payment `RegistrationModal`, visitor `RegisterRfidModal` and admin `EditRfidUserModal` (clearing it removes the field). Shown as a `.cell-sub` line under vehicle type/plate (Account Management, Recent Vehicle Activity, Active Visitor Passes, Search History tables) and in Search History details, receipt, Search History CSV (+ brand filter), Account Management/Reports search. VIP check-in (`CheckInGuestModal`) doesn't ask for it. There is no CSV/Excel **import** in the app - only exports.

**Google Forms import & registration processing** (Account Management -> "Imported" tab, admins only): `registrations/{id}` holds applicants who are NOT card holders yet (`models/registration.js`) - kept out of `rfidUsers` on purpose, because every `rfidUsers` record is something the ESP32 and gate logic act on. Import: `ImportRegistrationsModal` + `hooks/useRegistrationImport.js` + `utils/registrationImport.js` read .csv (hand-rolled RFC-4180 parser) or .xlsx (`read-excel-file@9.3.10`, lazy-loaded; v9 returns `[{ sheet, data }]` - first sheet used), auto-map Google Forms headers (the column-matching step is shown only when `mappingProblems` finds no Full Name / a field twice; otherwise the modal goes straight to a plain-language review: "N people will be added / already in iGate / have a problem" -> "Add N people"), never import password/PIN/token/key/secret columns (not even into the original copy), classify rows valid / incomplete / duplicate / invalid, then `services/firebase.js#importRegistrations` writes 50 rows per atomic multi-path update (row-by-row retry on a failed chunk). Blank or missing Role -> Student (the iGate form, Contact information section, asks Name, Plate Number, Vehicle Type, Vehicle Brand, Vehicle Color, Department, Role (Student only), Email, Contact Number - no Student ID/Course/Year). Required before Approved/Active: email or phone, role, vehicle type, plate (unless E-Bike/E-Scooter) - Student ID is NOT required, in `checkRegistration` and the rules. Incomplete rows are always added (Missing info), duplicates/invalid always skipped. Duplicates: `registrationKeys/{encoded sid:/email:/name: key}` -> registration id, written in the same update; the rules refuse a key owned by another registration (so re-importing a sheet creates nothing), plus client checks against existing owners (Student ID/email/plate) and within the file. Statuses: only the processing status is stored (`Pending Review` -> `Under Processing` -> `Approved` -> `Active`, or `Rejected`; transitions + "required fields complete before Approved/Active" + "Active only if the linked rfidUsers record is Active" are enforced in `database.rules.json`); account / payment / RFID status are derived from the linked owner record and its payments (`deriveRegistrationStatus`) - no duplicate status fields. `originalJson` (sheet row + first-imported fields) and `importedAt/By` are immutable in the rules; registrations can't be deleted from the app (Reject instead). Processing: `ProcessRegistrationModal` + `hooks/useRegistrationProcessing.js` (same "Registration Information" / "Vehicle Information" sections, order and placeholders as the Payment `RegistrationModal`; Student ID / Course / Year Level are not shown - any imported value is kept, just not editable; edit with "Submitted: ..." notes, Save as Pending, Approve, Reject/Reopen). RFID: `assignRegistrationCard` (scan via `useRfidScanner` = `devices/scanner/lastScan`) creates the owner record **Inactive** with `registrationId`/`studentId` - the ESP32 caches it as denied - refusing a card with an Active holder or reserved for another applicant; replace needs confirmation; `unassignRegistrationCard` frees it. Activation = the existing Payment `RegistrationModal` opened with `prefill` from Account Management -> `usePaymentRegistration` (now returns `rfidUserId`) -> `markRegistrationActive` (also releases a reserved card if a different one was scanned). Audit: `auditRegistrations` trigger (originalJson omitted). Account Management has no CSV/Excel/PDF export buttons anymore (removed on request; `ExportControls`, `utils/spreadsheetExport.js` and `write-excel-file` deleted) - `utils/csv.js#neutralizeFormula` still guards Search History/Reports CSVs.

**ALL CAPS fields**: names, plate numbers, departments and vehicle colors are uppercase (LTO/school-record convention); emails are never changed. `src/utils/textCase.js` (`CAPS_FIELDS`, `fieldInputValue`/`capsInputValue` - uppercases while typing without moving the cursor) is used by every form (Payment `RegistrationModal`, `RegisterRfidModal`, `EditRfidUserModal`, `AddExpectedGuestModal`, `CheckInGuestModal`), and `validateRfidUser`/`validatePayment` uppercase again on save. `expectedGuests` names are uppercased only in `createExpectedGuest`, never in `validateExpectedGuest` - a guard's check-in rewrites the record and the rules require every non-status field to stay byte-for-byte the same. Older mixed-case records are left as they are; every search is case-insensitive. **Plate numbers** are letters and digits only, any length up to 20 (`validators.js#PLATE_PATTERN`/`normalizePlate`, hint text `PLATE_FORMAT_HINT`): `textCase.js#plateInputValue` (via `fieldInputValue` for `PLATE_FIELDS`) drops spaces/hyphens/symbols while typing, forms prefill old values through `normalizePlate`, and `validateRfidUser`/`validatePayment`/`checkRegistration` strip them again on save - so an old "ABC-1234" record becomes "ABC1234" the next time it's saved. `expectedGuests` plates are only uppercased (not stripped) in the model, for the same byte-for-byte check-in reason as names.

**Master card** (offline manual override): one card id in the sketch's git-ignored `secrets.h` (`SECRET_MASTER_CARD_ID`, decimal, `0` = off) is checked before the authorization cache, so it works with no internet and must never be registered to a vehicle. Tap 1 opens both barriers and holds them (`masterHoldOpen`, persisted in `/masterhold.txt`; `scheduleAutoClose` is skipped), tap 2 closes both; any close (Gate Control, Serial tester) also ends the hold. Each tap goes to `overrideLogs/{id}` (`{ action: OPEN_BOTH|CLOSE_BOTH, cardId, timestamp, source: 'master-card', timeApprox? }`, queued in `/overrides.jsonl` offline) - never `gateLogs`, so it isn't a vehicle IN/OUT. Rules: staff read-only, no client write. Shown as the last 5 on `GateStatusCard` (`listenToOverrideLogs`). A power cut still needs the barrier's own manual release or a backup battery.

**UHF reader** (firmware): trigger on GPIO7 (active LOW) - switched off on every real card read and re-armed by an `esp_timer` 1.5 s after the read (`RFID_TRIGGER_COOLDOWN_MS`), even while the scan is still uploading; the same card read again within 3 s restarts its cooldown, so a waiting car is never logged twice. Only a NEW read (accepted or denied) pauses the reader; an ignored read (same card still in cooldown, or a motor running - `isIgnoredRead`) leaves it on and skips the `lastScan` publish, so the first car's tag sitting under the reader can't starve the next car's tag. The camera's IP is cached for 5 min (`lookupCameraHost`), and the ESP32-CAM's `/trigger` answers as soon as the photo is captured, before the upload, so an IN scan no longer holds the next car up for the upload. Frames are latched in the ISR on a microsecond gap and accepted only at 26-34 bits with valid parity (26/34) or an identical repeat (other lengths); D0/D1 swap is auto-corrected. A valid id from this reader is Wiegand-26 including parity, so always < 67,108,864 - anything larger stored in `rfidUsers.rfidId` is a corrupted read and must be re-scanned. Type `help` in the Serial Monitor for the built-in tester.

**Logout**: one implementation - `LogoutConfirmModal` (confirm -> `services/auth.js#logOut` -> `/login`), opened from the top-bar account menu, System Settings, the Pending page and the sidebar's bottom-anchored Logout button (`.sidebar-footer`; on phones it closes the drawer first and the dialog is portalled to `<body>` so the drawer's slide-out transform can't carry it away). **Username login**: the login box takes an email (contains "@" -> `signInWithEmailAndPassword`, unchanged) or a username. Firebase Auth only knows emails, so a username is resolved server-side by the `signInWithUsername` callable (`functions/index.js`): `usernames/{key}` -> uid (key = username with "." as ","; server-only node, no client read/write), it checks the password against Firebase Auth's own REST sign-in, and only then returns `createCustomToken(uid)`; the client signs in with `signInWithCustomToken`. The email is never returned, nothing about the password is stored, "unknown username" and "wrong password" give the same error, and failures are throttled per IP (`usernameLoginThrottle/`, server-only, 10 per 15 min). Usernames are claimed/changed ONLY via the `setUsername` callable (own account, transaction = unique; rules: `adminProfiles/{uid}/username` can't be changed by any client) - at sign-up (`signUp` undoes the whole account if the name is taken) or in My Profile (`UsernameField`). `releaseUsername` frees a name when its profile is deleted. Rules for a valid username: `src/utils/validators.js#USERNAME_PATTERN`, hand-copied in functions/index.js. **Production needs** the functions' service account (`<project-number>-compute@developer.gserviceaccount.com`) to have the "Service Account Token Creator" role, or `createCustomToken` fails (username login only; email login unaffected). Forgot password still goes by email.

**Security hardening (2026-10-17)** — supersedes older notes above where they differ; `pre-security-fixes-2026-10-17` tag = the state before:
- **Admin checks require Active**: every `adminProfiles` rule that grants Super Admin/Administrator powers also requires the caller's own `status === 'Active'` (a deactivated/locked admin can't reactivate themselves or approve signups).
- **Fixed set of two Super Admins** (`test@bulsu.edu.ph`, `igatebustosmis@bulsu.edu.ph`): Super Admin is not in `ASSIGNABLE_ROLES` (signup dropdown, Staff Accounts dropdown, `canApproveRole`), and `database.rules.json` refuses any client write that makes someone a Super Admin, changes a Super Admin's role or status, deletes a Super Admin profile, or sets `requestedRole: 'Super Admin'`. Super Admin rows in Staff Accounts are read-only. Adding/removing one is done only in the Firebase console (Authentication + `adminProfiles/{uid}`).
- **Own-profile writes**: owners may write their profile only while it is missing (signup), `Pending` or `Active`; an `Inactive` owner may only delete it (Start over); a legacy `Locked` owner can't write at all.
- **No account lockout**: the 5-failed-sign-ins lock (`checkLoginLock`/`recordFailedLogin`/`resetLoginAttempts`/`unlockAccount`, Locked Accounts panel) was removed. Its unauthenticated callables let anyone lock any account (incl. Super Admins), leaked which emails exist, and let a Pending signup restore itself as `Active`. Wrong passwords are now throttled by Firebase Auth's own server-side limiter (`auth/too-many-requests`) plus `LoginForm`'s escalating cooldown. `Locked` stays a valid status only for leftover records - a Super Admin can Reactivate one (if its Firebase Auth login is still disabled, re-enable it in the console: Authentication -> user -> Enable).
- **rfidUsers**: a non-admin can't change an existing record's `role` TO `Visitor` (that + the Visitor return rule let a guard deactivate anyone), and can create a non-`Visitor` record only together with a brand-new `payments/{paymentId}` for the same card received by them (atomic update). Still open by design: a guard can issue a free Visitor pass and later edit it to another role.
- **payments**: new entries must have `amount > 0` matching the fee table.
- **gateLogs**: non-admin creates must use source `simulated`/`visitor-return`/`vip-checkout` and a timestamp within ±5 min of server time (only the ESP32, via its secret, writes `esp32-*` sources / old buffered times).
- **settings/app/gateStatus/{entrance,exit}**: `.validate: false` for every client - only the ESP32 (legacy secret) writes it. **`SET_AUTO_CLOSE`** command is admin-only in the rules too.
- **SMS**: `sendGateScanSms` sends at most 1 text per phone per 30 s and 20 per Manila day (server-only `smsRate/{phone}`); skipped ones are logged in `smsLogs` as `rate-limited`.
- **Storage**: `vehicle-snapshots/` read/create require the `staff: true` custom claim, which `syncStaffClaims` (trigger on `adminProfiles/{uid}`) sets for Active profiles and clears otherwise; `services/firebase.js#ensureStorageAccess` calls the `refreshStaffClaims` callable + forces a token refresh before an upload. Uploads are create-only (no overwrite/delete). Revocation takes effect when the user's token next refreshes (≤ 1 h).
- **Audit log**: `functions/index.js#auditTrigger` (1st-gen `firebase-functions/v1` RTDB `onWrite` triggers on purpose - only they report `context.auth`/`context.authType`; the 2nd-gen ones don't) copies every change to `adminProfiles`, `rfidUsers`, `payments`, `expectedGuests`, `devices/scanner/command`, staff-made/edited/deleted `gateLogs` (not ESP32 scans or camera `imageUrl` backfills) and `settings/app` (not ESP32 `gateStatus` moves) into `auditLogs/{push}`: `{ at (event time), entity, entityId, action, by (uid or 'system' = ESP32/function/console), byName, byRole, changes: { field: { from?, to? } } }`. Rules: read = active Super Admin only, no client write. Shown in Account Management's `AuditLogPanel` (Super Admin only, `useAuditLogs` -> `listenToAuditLogs`, last 500, filter/search/CSV). Incident-response steps live in README.md.
- **Forgot password / email links**: `LoginForm` (forgot mode) validates the email, always shows the same "if an account exists" message, and allows one send per 60 s. The links in Firebase's emails open `/auth/action` (`AuthActionPage` + `hooks/useAuthAction.js`) - this requires Firebase console -> Authentication -> Templates -> "Customize action URL" = `https://igate-bulsu.web.app/auth/action` (one setting for every template, so the page also handles `mode=verifyEmail`). It only calls Firebase's `verifyPasswordResetCode`/`confirmPasswordReset`/`applyActionCode` (codes, one-time use and 1-hour expiry stay Firebase's) and enforces the app's `PASSWORD_RULES`, which Firebase's default page (6 chars) didn't. Afterwards it sends the user to `/login` with their email prefilled.
- `utils/csv.js` prefixes `'` to text cells starting with `= + - @` (CSV formula injection).
- Deploy all of it together: `firebase deploy --only database,storage,functions`.

## Known issues to be aware of

**Sign-up, email verification & admin approval** (`/signup` → `SignupForm.jsx`, `/pending` → `PendingApprovalPage.jsx`, both public routes; `signUp()`/`refreshEmailVerified()`/`resendVerificationEmail()` in `src/services/auth.js`): a signup picks a role from a dropdown but that is only a **request**. `signUp()` creates the Auth account and writes `adminProfiles/{uid}` with `status: 'Pending'`, the harmless interim `role: DEFAULT_SIGNUP_ROLE` (`Security Guard`), the picked role in `requestedRole`, and `emailVerified: false`, then calls `sendEmailVerification` (Firebase's default email, which contains the verify link). `RequireAuth` redirects any `Pending`/`Inactive` profile (`status` from `useAuth()`) to `/pending`, which shows the two steps (verify email via `useEmailVerification`, then wait for an admin) and flips to the dashboard automatically once status becomes `Active`. `Inactive` is also how a declined request is stored. Approvals live in `PendingApprovalsPanel.jsx` (top of Account Management): each row shows the **requested role** and whether the email is verified; Approve is disabled until the email is verified, and `canApproveRole()` (`src/constants/roles.js`) limits an Administrator to approving `Security Guard` requests while a Super Admin can approve any. Approve = targeted `update({ role: requestedRole, status: 'Active' })`, never a full `set()`. Deactivating/reactivating an existing staff account is a Super-Admin-only Deactivate/Reactivate button in Account Management's Staff Accounts table (`setAdminStatus`, same targeted-update pattern; you can't deactivate yourself): `Inactive` locks the account out of every database path via the rules and bounces it to `/pending`, but does not disable the Firebase Auth login itself.

`database.rules.json` is the real enforcement, not the UI: (1) every non-`adminProfiles` node now requires the caller's own `adminProfiles/{uid}/status === 'Active'` (so Pending/declined accounts — and Auth accounts with no profile at all — can read/write nothing); (2) a user can only create their *own* profile as `status: 'Pending'` with `role: 'Security Guard'`, and can never change their own `role`/`status`/`requestedRole`; (3) Pending → Active requires `emailVerified === true`, and `emailVerified` can only be set to `true` by the profile's owner while their auth token says `email_verified` (the client force-refreshes the ID token first); (4) Administrators can read *only* the `status == 'Pending'` query of `adminProfiles` and write only Pending records, only approving `Security Guard` requests; Super Admins can do everything. Consequences: the first Super Admin/Administrators must still be provisioned in the Firebase console **with `status: 'Active'`** on their `adminProfiles/{uid}` record (an existing profile without it is locked out of everything once these rules are deployed); the old self-toggle on My Profile's status pill was removed (status is admin-controlled now); and `storage.rules` matches via a custom claim (see Security hardening below). Deploy with `firebase deploy --only database`.

**Recovering from a bad signup** (e.g. a mistyped email that can never verify): `/pending` has a password-confirmed "Cancel signup & start over" (`CancelSignupModal`, `useCancelSignup` -> `reauthenticate` + `deleteOwnAccount` in `services/auth.js`) that deletes the user's own `adminProfiles/{uid}` and Firebase Auth login so the email can be reused; it's available to Pending and Inactive accounts (so a deactivated staff member could delete their own record too - accepted). A Super Admin can also **Remove** an Inactive profile from Account Management's Staff Accounts table (`deleteAdminProfile`); that deletes only the RTDB record, since a client can't delete another user's Auth login - the removed user, on next sign-in, lands on `/pending` as "Account removed" (`RequireAuth` now sends a profile-less login, `status` null, there instead of letting it through) and can use "Start over" to clear their login. No rules changes: `adminProfiles/{uid}` `.write` already allows the owner or a Super Admin, and deletes skip `.validate`.

Assigning a *different* user's role (e.g. a Super Admin promoting a Security Guard to Administrator) has no UI anywhere in the app — `database.rules.json` only allows a user to write their own `adminProfiles/{uid}`, and only when their own current role is already `Super Admin` (or the profile doesn't exist yet and the role being set is `Security Guard` — the self-signup path). Cross-user role assignment today means editing `adminProfiles/{otherUid}/role` directly in the Firebase console. Building an in-app user-management screen for this is a natural next step but out of scope until asked for.

Because `System Settings` is now Super-Admin/Administrator-only (`ADMIN_ROLES` in `src/constants/roles.js`), and "My Profile" / "Change Password" are only linked to from `SettingsPage`, a Security Guard currently has no in-app way to reach `/profile` or open `ChangePasswordModal` even though the `/profile` route itself has no role restriction. If this needs fixing, it means adding a role-independent entry point to those (e.g. in `AppShell` or the top bar), not loosening the `/settings` guard.

`ChangePasswordModal` (`src/components/modals/ChangePasswordModal.jsx`) reauthenticates with the current password via `reauthenticateWithCredential`/`EmailAuthProvider` before calling `updatePassword` — both from `firebase/auth`, using `auth.currentUser`. It shows a friendly error if there's no real signed-in user (this used to matter for the login bypass; the bypass has since been removed, so `auth.currentUser` should always be real now for anyone who successfully reaches an authenticated route).
