# iGATE Capstone Project (SKUL JUAN) - System Architecture & AI Guidelines

## 1. Safety Guardrails & Logic Preservation (Strict)
- **UI vs. Logic Isolation:** Never remove, refactor, or simplify existing state hooks (`useState`, `useEffect`), Firebase RTDB listeners, or business logic when performing UI/layout updates. Always preserve non-UI code line-for-line.
- **Strict Modification Constraint:** You are strictly forbidden from modifying state management, backend logic, or hardware handlers unless the prompt explicitly requests a logic change.

## 2. Architecture & Clean Code Rules (Anti-"Vibe Code")
- **Layered Architecture:** Keep UI components strictly for rendering layout. Abstract all Firebase operations and business logic into dedicated Custom Hooks (`/src/hooks`) or Service Classes (`/src/services`).
- **DRY Principle (Don't Repeat Yourself):** Avoid redundant inline code or duplicate UI elements. Reuse base components (e.g., Modals, Tables, Stat Cards) via generic props instead of creating single-use components.
- **Single Responsibility:** Each file must do ONE thing well. UI handles presentation; Hooks handle state/events; Services handle Firebase/hardware communications.

## 3. Communication & Code Quality Guidelines
- **Smarter & Direct Responses:** Skip unnecessary pleasantries or fluff. Provide concise explanations and direct, precise code edits.
- **Git Milestones:** Suggest clean git commits after achieving major, stable functional milestones.

# CLAUDE.md (Original Repository Context & Architecture)

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.


## What this is

iGate - a vehicle gate access & tracking system for Bulacan State University (Bustos Campus). React SPA (Vite) with Firebase (Auth + Realtime Database) as the backend. Staff log in and manage gate access logs, vehicle/account registration, payments, reports, and RFID-based entry/exit records.

## Commands

```bash
npm install     # install dependencies
npm run dev     # start Vite dev server
npm run build   # production build
npm run serve   # preview the production build
```

There is no lint script, no test runner, and no test files in this repo currently.

## Architecture

**Routing** (`src/App.jsx`): `react-router-dom` v6 nested routes, each top-level route rendering a `*Wrapper` component. `/login` is public; every other route is nested under `<RequireAuth />` (`src/components/auth/RequireAuth.jsx`), which redirects to `/login` if `AuthContext`'s `user` is null. `/account-management` and `/settings` are additionally nested under `<RequireRole allowedRoles={ADMIN_ROLES} />` (`src/components/auth/RequireRole.jsx`), which redirects non-admins to `/dashboard`. `ADMIN_ROLES` and the full `ROLES` list live in `src/constants/roles.js` — currently `Super Admin`, `Administrator`, `Security Guard` (no `Staff` login role; don't reintroduce it). `Sidebar` (`src/components/sidebar/Sidebar.jsx`) filters nav items by the same `roles` list so guarded pages aren't shown as dead links.

**Page composition pattern**: every feature folder under `src/components/` follows `Wrapper -> AppShell -> Page`:
- `FooWrapper.jsx` wraps `FooPage.jsx` in `AppShell` (see `src/components/dashboard/DashboardWrapper.jsx` for the canonical example).
- `AppShell` (`src/components/layout/AppShell.jsx`) renders the `Sidebar` plus a `<main>` content area, and reads/writes sidebar-open state via `AppStateContext`.
- Follow this same three-file pattern when adding a new top-level route.

**Global state** — two small context providers wrap the whole app in `App.jsx`:
- `AuthContext` (`src/context/AuthContext.jsx`): subscribes to Firebase `onAuthStateChanged`, then subscribes to `adminProfiles/{uid}` for the signed-in user's `role`, exposing `{ user, role, loading }` via `useAuth()`. `loading` stays true until both the auth state *and* the role fetch have resolved, so route guards don't flash the wrong content mid-login.
- `AppStateContext` (`src/context/AppStateContext.jsx`): a single `useReducer` for cross-cutting UI state — `sidebarOpen` and `activeModal` (`{ type, ...payload }`). Some modals (Payment's `RegistrationModal`, `RemarkModal`) are opened via `dispatch({ type: 'OPEN_MODAL', ... })` and rendered off `state.activeModal?.type` — prefer this for anything cross-cutting. In practice it's not universal: `RegisterRfidModal` (Dashboard), and `EditRfidUserModal`/`ConfirmModal` (Account Management) use plain local `useState` instead, since they're single-page-scoped and don't need to be reachable from elsewhere. Match whichever pattern the modal you're touching already uses rather than assuming one is canonical.

**Firebase** (`src/services/firebase.js`): initializes the v9 modular SDK and exports `auth` (Firebase Auth) and `rtdb` (Realtime Database — **not** Firestore; there is no `getFirestore()` call anywhere in this app). Config is currently hardcoded inline (not in an untracked `.env`, even though `.env` is gitignored) — do not add secrets beyond what's already there without checking with the user first. `src/services/auth.js` wraps `signInWithEmailAndPassword`/`signOut`.

**Data is live, backed by the Realtime Database.** Every top-level page (dashboard, payment, search-history, accounts, reports, settings) subscribes to `firebase.js` listeners (`listenToGateLogs`, `listenToRfidUsers`, `listenToPayments`, `listenToAdminProfile`) or the `useEnrichedGateLogs`/`useRfidScanner` hooks — none of them render hardcoded sample arrays anymore. RTDB paths in use: `gateLogs` (RFID scans), `rfidUsers` (registered vehicles/owners), `payments`, `adminProfiles/{uid}` (per-admin profile, keyed by Firebase Auth uid), `settings/app`, `users/system`.

`ProfilePage` falls back to a `localStorage` copy (`igate_admin_profile`) only when there is no authenticated `user` — every real login persists to `adminProfiles/{uid}` in RTDB instead, and the email field becomes read-only in that case since changing it here wouldn't actually update Firebase Auth.

`SettingsPage`'s "Recent Logs" panel merges real RTDB gate-scan history (via `useEnrichedGateLogs`) with locally-generated session events (gate toggle clicks, login) — the gate open/close buttons themselves are still local-only UI state, not wired to any hardware/RTDB command path.

There is no Firestore usage anywhere in this app. RTDB security rules **are** version-controlled: `database.rules.json` (repo root) is the source of truth, deployed to the Firebase console's Rules tab — `firebase.json` points the Firebase CLI at it for `firebase deploy --only database`. Rules require `auth != null` on every path, scope `adminProfiles/{uid}` to its own owner, and structurally validate writes to match the shapes in `src/models/`. Changing a write shape in `src/services/firebase.js` without updating both the matching `src/models/*.js` validator and `database.rules.json` will make writes fail silently against real rules even though local dev (which uses the same rules) may still pass if you haven't deployed the latest rules yet.

**Data models** (`src/models/*.js`): one file per RTDB entity (`gateLog`, `rfidUser`, `payment`, `adminProfile`, `appSettings`, `systemUser`), each exporting a JSDoc `@typedef` and a `validate*()` function that normalizes and throws on invalid shape. Every write in `src/services/firebase.js` runs its payload through the matching validator before `set()`/`push()`. This is plain-JS runtime validation, not TypeScript — the repo has no TS toolchain, don't introduce one for this without asking. `rfidUser`'s `role` field (Student/Faculty/Staff/Visitor — the vehicle owner's category) is unrelated to the admin login `role` in `src/constants/roles.js`; don't conflate the two. `rfidUser` also has `email` (optional, format-checked) and `status` (`Active`/`Inactive`, default `Active`) — format/enum patterns live in `src/utils/validators.js` (`isValidRfid`, `isValidPlate`, `isValidEmail`) and are shared between the model validators and every registration/edit form's inline field checks, so the two never drift apart.

**RFID user CRUD** (`src/services/firebase.js`): `registerRfidUser` (strict-create, throws on duplicate RFID — used by the Dashboard's "Register RFID" button) and `upsertRfidUser` (create-or-renew, never throws on an existing RFID — used by the Payment registration/renewal flow) are both open to any authenticated role, since Security Guards legitimately create/renew via those two entry points. `updateRfidUser` (full-field edit, Account Management's Edit modal), `deleteRfidUser`, and `setRfidUserStatus` (deactivate/reactivate) are the three actions gated to `ADMIN_ROLES` — enforced at the route level (`/account-management` is already admin-only) *and*, for delete/status specifically, at the RTDB rules level too (see below), because those two are meaningfully distinguishable from a guard's create/renew at the rules layer in a way a generic "edit" isn't.

**Why `database.rules.json`'s `rfidUsers` write rule looks the way it does**: RTDB rules see only the resulting data diff, not which UI screen or business operation produced it — so "Account Management edit" and "Payment renewal" are indistinguishable from the rules' point of view when both do a `set()` on an existing record. The rule therefore allows any authenticated role to create-or-update a record (`newData.exists()`), but requires `Super Admin`/`Administrator` when the write is a delete (`!newData.exists()`). The `status` child has its own `.validate` requiring the value be unchanged (fine for a guard's renewal `set()`, which resends the same status) or the actor already be an admin — this is what actually makes deactivate/reactivate admin-only, since the outer `.write` rule alone can't express it. If you touch this rule, keep both branches in mind or you'll either lock guards out of registration or let them silently deactivate accounts.

**Hardware note**: the physical RFID reader (`sketch_scanner.ino`, ESP32) POSTs directly to `gateLogs` over the RTDB REST API using a legacy database secret (`FIREBASE_AUTH` in the sketch), not Firebase Auth — a valid secret bypasses `database.rules.json` entirely, so the `auth != null` rule on `gateLogs` does not affect it. If `FIREBASE_AUTH` is ever blank in the sketch, the scanner depends on the rules being fully public and will silently stop logging scans the moment `database.rules.json` is deployed. A raw `gateLogs` entry only ever has `cardId`/`cardHex`/`direction`/`timestamp` (that's all the hardware knows) — never assume it carries `name`/`plateNumber`/etc. directly; always go through `useEnrichedGateLogs` (`src/hooks/useEnrichedGateLogs.js`), which joins each scan against `rfidUsers` by normalized `cardId`/`cardHex`, to get those fields.

**Live dashboard metrics** (`src/hooks/useGateStats.js`): computes `totalRegisteredVehicles` (active `rfidUsers` count), `vehiclesInsideCampus`, `todaysEntries`, `todaysExits` from the full `gateLogs` + `rfidUsers` listeners — rendered by `StatsCards`. "Inside campus" requires finding each card's single most recent scan across the *entire* history (a `Map` keyed by normalized `cardId`/`cardHex`, keeping whichever entry has the latest `timestamp`), so it can't be derived from a single new event — that's why this hook uses the full-history `listenToGateLogs` (`onValue`), not the event-stream one below.

**Hardware-ready live feed** (`listenToNewGateLogs` in `src/services/firebase.js`): uses RTDB's `onChildAdded` instead of `onValue` — the same event type a real ESP32 write triggers — filtered to entries timestamped after the listener attached (so the initial backlog burst `onChildAdded` always sends on mount isn't treated as "new"). Currently drives the "just scanned" row flash in `RecentActivityTable` and the "last scan received" live timestamp on `DashboardPage`; reach for this (not `listenToGateLogs`) for anything that should react to a single new scan as it happens rather than the whole list.

**Simulating hardware without physical scanner present**: `SimulateScanModal` (`src/components/dashboard/SimulateScanModal.jsx`, admin-only, triggered from `DashboardPage`) calls `logGateEntry` — the exact same function/validation path (`validateGateLog`) a real hardware-authenticated write would eventually reuse if the ESP32 ever posts through the app instead of raw REST. Useful for exercising the live dashboard/stats during development.

**Remarks feature**: `useRemarks` (`src/hooks/useRemarks.js`) persists free-text remarks per RFID to `localStorage` (key `igate_user_remarks`), not Firestore. Used by the dashboard and search-history activity tables together with `RemarkModal` and the `RemarkAddButton`/`RemarkTick` components in `src/components/shared/RemarkBadge.jsx`. Note the keying isn't consistent: `RecentActivityTable` keys remarks off the gate-log entry's own id (per scan event), while `SearchHistoryPage` keys off `person.rfidId` (per person) — this predates Phase 4 and wasn't changed, just preserved as-is.

**`SearchHistoryPage.jsx` has two independent sections**: the original single-person lookup (search by Plate/RFID/Name → one matched `rfidUsers` record + their own scan history) is unchanged, and a second "All Entry & Exit Logs" section below it is a general filterable/sortable/paginated table over every `useEnrichedGateLogs()` entry (date range, vehicle type, RFID, driver name filters; click `Time`/`Name` headers to sort; CSV via `src/utils/csv.js#downloadCsv` — no library, a hand-rolled `Blob` download — and PDF via `window.print()`, matching the same pattern `PaymentPage`/`ReportsPage` already use). `ReportsPage.jsx` has a similar-looking filter/table of its own that predates this — the two overlap in purpose but haven't been consolidated; don't assume one supersedes the other without asking.

**Barrier gate control** (`src/components/dashboard/GateStatusCard.jsx`, Phase 6): shows a live OPEN/CLOSED/UNKNOWN badge for the physical gate and, for any of the three staff roles (`ROLES`, not `ADMIN_ROLES` — Security Guards need this too, and it's on the Dashboard rather than System Settings specifically because `/settings` is admin-only), a manual override button (reusing `GateButton`, the same component `SettingsPage`'s local-only toggle uses) that goes through a `ConfirmModal` before writing. State lives at `settings/app/gateStatus` (`{ state, updatedAt, updatedBy, updatedByName }`, `src/models/appSettings.js#validateGateStatus`), written via `setGateStatus`/read via `listenToGateStatus` in `services/firebase.js` — always as a targeted leaf write, never through `validateAppSettings`/`initializeFirebaseCollections`, so a gate toggle can never clobber `appName`/`campus`/etc., and the once-per-app-mount `initializeFirebaseCollections()` call can never stomp a live gate state back to a default. A physical ESP32 relay controller is expected to read (and eventually write) this same path the way `sketch_scanner.ino` already reads/writes `gateLogs` today — over the RTDB REST API using a legacy database secret that bypasses `database.rules.json` entirely (see the hardware note below) — so no relay firmware exists in this repo yet and no rule was added to make the node publicly readable; `database.rules.json` only adds a `.validate` on `gateStatus` for shape (`state` must be `OPEN`/`CLOSED`, `updatedAt` a number).

**Visitor management & SMS alerts** (Phase 7): `rfidUser` (`src/models/rfidUser.js`) gained four fields, all optional: `phone` (canonical `09XXXXXXXXX`, normalized/validated by `normalizePhone`/`isValidPhone` in `src/utils/validators.js`), `expiresAt` (ms epoch, visitor-pass expiry), `hostName`, `purpose` (visitor-only, who/why). Visitors are **not** a separate RTDB node — they're `rfidUsers` with `role: 'Visitor'`, so they show up in every existing table (Dashboard, Search History, Account Management) for free; nothing auto-deactivates a record once `expiresAt` passes, that's advisory only today. `RegisterRfidModal.jsx` (Dashboard, guard-reachable) conditionally shows Host Name/Purpose/"Pass Valid For" fields and swaps its title/submit label to "Register Visitor Pass"/"Issue Visitor Pass" when `role === 'Visitor'` is selected — this is also where `expiresAt` gets computed from the chosen duration. `EditRfidUserModal.jsx` (Account Management, admin-only) also gained a `phone` field so existing records can be corrected. `.modal-card` picked up `max-height: 90vh; overflow-y: auto` here too — the visitor fields made this modal tall enough to overflow a fixed-position backdrop with no scroll, which would have made the submit button unreachable on shorter viewports; this fix applies to every modal built on `.modal-backdrop`/`.modal-overlay` + `.modal-card`, not just this one.

SMS is sent by a new Cloud Function, `functions/index.js` (`sendGateScanSms`, an `onValueCreated` trigger on `/gateLogs/{logId}`) — **not** from client code, because the Semaphore API key must never ship in the JS bundle. It re-derives the same cardId/cardHex → `rfidUsers` match as `src/hooks/useEnrichedGateLogs.js` (hand-copied, not imported — `functions/` is a separate Node package/runtime with no bundler linking the two; keep both in sync by hand if the match logic ever changes), and if the matched owner has a `phone`, POSTs to Semaphore's `v4/messages` endpoint and writes an audit record to `smsLogs/{logId}` (`database.rules.json`: client `.read` only, no client `.write` — the Admin SDK write bypasses that the same way the ESP32's legacy database secret bypasses rules for `gateLogs`, see the hardware note above). Fires on both IN and OUT scans. The Semaphore API key is a Cloud Functions **secret** (`defineSecret('SEMAPHORE_API_KEY')` from `firebase-functions/params`, bound via the trigger's `secrets:` option) — set once via `firebase functions:secrets:set SEMAPHORE_API_KEY` (run by a human, never through chat/AI tooling), not `functions.config()` (deprecated) and not a plain env var. `SEMAPHORE_SENDER_NAME` is a non-secret `defineString` param (default `SEMAPHORE`, overridable via `functions/.env`, see `functions/.env.example`). Deploying `sendGateScanSms` requires the Blaze (pay-as-you-go) plan — Semaphore is a non-Google outbound HTTP call, which the free Spark plan blocks entirely regardless of secrets being configured. As of this writing no Semaphore account/API key has been provisioned yet, so this function is written and installs cleanly (`node --check` passes, `npm install` in `functions/` succeeds) but has never actually been deployed or sent a real SMS — do that only after the secret is set.

**`StatsCards.jsx`** was rebuilt in Phase 4 to show exactly `Total Registered Vehicles` / `Vehicles Inside Campus` / `Today's Entries` / `Today's Exits` (via `useGateStats`), replacing an earlier Car/Students/Faculty/Motorcycles/Total breakdown sourced from `rfidUsers`. That breakdown is gone, not hidden — if it's still wanted, it needs to be re-added as a separate component rather than assumed to still exist.

**RBAC audit & RTDB hardening** (Phase 9): `RequireAuth`/`RequireRole` (`src/components/auth/`) and the `/dashboard`, `/search-history`, `/reports`, `/payment`, `/profile` (any authenticated role) vs `/account-management`, `/settings` (`ADMIN_ROLES` only) route split in `App.jsx` were audited and found already correct — not rebuilt, per this project's own strict-modification rule. What the audit actually found and fixed was at the **RTDB rules layer**, since `RequireRole` is a UX convenience, not the real security boundary — the real boundary is `database.rules.json`, and several existing rules were more permissive than the frontend's own intent:
- `rfidUsers/{id}/rfidId` (which physical card a record is bound to) can now only be *changed* by an admin once a record exists — any authenticated role can still set it on first create (registration). Previously any authenticated role could silently reassign an existing record to a different card via direct Firebase access, even though no guard-facing flow ever does that (registration is create-only; renewal is looked up *by* rfidId).
- `gateLogs/{id}` and `payments/{id}` are now effectively **append-only** for non-admins: creating a new entry is unrestricted (matches how the ESP32/`SimulateScanModal`/`recordPayment` already only ever `push()` new entries), but modifying or deleting an *existing* entry is admin-only. `gateLogs`' `imageUrl` child is the one exception (still freely settable by any authenticated role, unchanged — `uploadVehicleSnapshot` needs this). Previously any authenticated role could silently rewrite or delete gate-log/payment history via direct Firebase access, which nothing in the frontend ever does or needs to do.
- `settings/app` (`appName`/`campus`/`status`/`createdAt`) is now Super Admin/Administrator-only to write, **except** `settings/app/gateStatus`, which deliberately keeps `"auth != null"` — Phase 6 intentionally lets Security Guards trigger the manual barrier-gate override from the Dashboard, and this phase must not break that. The child's own more-permissive `.write` rule works via RTDB's cascading semantics (a deeper rule can grant access a shallower one denies) — see the inline comments in `database.rules.json` and `firebase.js#setGateStatus` for how these two rules coexist.
- `App.jsx`'s `initializeFirebaseCollections()` bootstrap call is now gated to `ADMIN_ROLES` only (previously ran for every authenticated user on every mount) — a direct consequence of the `settings/app` change above, since a Security Guard would otherwise get a harmless-but-noisy `permission-denied` console error on every login.

`scripts/verify-firebase.mjs` was extended to be **role-aware**: it reads the signed-in test account's own role back from `adminProfiles/{uid}` and picks `expectAllowed`/`expectDenied` per admin-gated check based on that, so the exact same script correctly validates either direction depending on which account's credentials it's run with — run it once with a Security Guard account and once with an Administrator/Super Admin account to fully exercise the RBAC boundary. (No credential was ever entered by the assistant to do this — that's a deliberate, standing constraint: passwords are never handled in chat/AI tooling, even for test accounts.)

**Offline RFID authorization cache** (Phase 9, firmware): lives in the *sibling* `sketch_scanner` repo (`c:\Users\Cener\OneDrive\Documents\CAPISTON\sketch_scanner\sketch_scanner.ino`), not this one — flagged here because it's tightly coupled to this repo's schema. Extends the Phase 8 offline-buffering ESP32 firmware with a local, LittleFS-cached snapshot of `rfidUsers` (`rfidId`/`status`/`plateNumber`/`vehicleType` only — task constraint was "don't store unnecessary Firebase data"), refreshed every 5 minutes while online via the same legacy-secret REST pattern the sketch already uses for `gateLogs`. When offline (or a live POST fails despite Wi-Fi being connected), a scan is checked against this cache before being buffered: authorized (registered + Active) → buffered to `/buffer.jsonl` with `plateNumber`/`vehicleType` now embedded on the JSON line (`gateLogs` has no rule restricting extra fields, so this is additive/inert to everything already reading that node); unauthorized (inactive, unknown, or no cache loaded yet) → denied and Serial-logged only, never buffered — per the user-supplied flowchart, "Deny Access" is a terminal state with no path to the buffer. A sync only ever replaces the on-disk/in-memory cache after a *fully successful* fetch+parse; any failure leaves the last-known-good cache untouched, so a bad network moment can never leave the gate with zero authorization data. Requires a new Library Manager dependency, **ArduinoJson v7** (not bundled with the ESP32 core) — parsing arbitrary incoming Firebase JSON by hand, unlike Phase 8's buffer lines which the sketch fully controls the shape of itself, was judged too risky for a security-relevant authorization decision.

**Payment, fees & document verification** (Phase 10): the Payment page's `RegistrationModal` (opened via `AppStateContext`, wide two-column layout with a live receipt panel) is the one registration path for Student/Faculty/Staff; the Dashboard's `RegisterRfidModal` is now **visitor-only** (temporary pass, visitor leaves a valid ID at the guardhouse) so nothing can be registered without paying, verification and consent. Pricing lives in `src/constants/fees.js` (`VEHICLE_FEES`: Motorcycle 50, Tricycle 75, Car/Truck 100 - large EVs register as Car; E-Bike/E-Scooter 50 is a placeholder; same fee for Registration and Renewal), together with `REGISTRATION_VALIDITY_MONTHS` (5, **unconfirmed by the university** - change only there), the per-vehicle-type required documents (`license`+`orcr` for motor vehicles, `validId` for e-bike/e-scooter, plate optional for those two), and the privacy-consent text/version. Documents are **verify-only**: the guard ticks that the originals were checked (+ license expiry date, expired = blocked); nothing is scanned or uploaded, so there are no document images to protect - what's recorded, on the append-only `payments/{id}`, is `docsVerified`, `licenseExpiry`, `consentAt`, `privacyNoticeVersion`, `receivedBy`/`receivedByName`, `amountTendered`/`change` (`amount` stays the fee charged, which "Total Collected" sums) and a sequential `receiptNo` from a transaction on `counters/receipt` (`getNextReceiptNo`; a failed payment write after it leaves a gap, never a duplicate). `database.rules.json` forces `receivedBy === auth.uid` on create, `amountTendered >= amount`, and `counters/receipt` may only increment by 1 - **these rules must be deployed** (`firebase deploy --only database`) or registration fails on the counter write. Fee correctness is client-side only (fees aren't in the rules, so changing a fee never needs a rules deploy); moving fees to `settings/app/fees` with a Super Admin-only write would let rules enforce it. The write sequence lives in `hooks/usePaymentRegistration.js` (upsert `rfidUsers` -> next receipt no -> `recordPayment`); `ReceiptModal`/`ReceiptSummary` render the receipt and share `PrintPreviewFrame` with `PrintReportModal`. `rfidUser` gained optional `vehicleColor`; `VEHICLE_TYPES` gained `Tricycle` and `E-Scooter`.

**VIP pre-clearance & visitor pass return** (Phase 11): a new `expectedGuests/{id}` node (`src/models/expectedGuest.js`) lets an Administrator pre-clear a guest (`VipGuestsPanel`, Account Management: name, category — `Guest Speaker`/`University Dignitary`/`Government Official`/`VIP Event` — host, optional purpose/plate, an arrival window) so they never queue or hand over an ID at the gate. A guard checks them in/out from the Dashboard's `GuestClearancePanel` (visible to all three roles, same as the rest of the Dashboard) without needing an admin: **Check In** (`checkInGuest`) scans a temporary card and issues it as an ordinary `rfidUsers` record with `role: 'Visitor'`, `expiresAt` = the guest's `validUntil`, `hostName`/`purpose` carrying the category — the exact same shape a walk-in visitor pass already has, so it shows up everywhere those do — then flips the guest to `Arrived`; **Check Out** (`checkOutGuest`) deactivates that pass and flips the guest to `Departed`. No payment is recorded - VIP guests don't pay the registration fee. `database.rules.json`'s `expectedGuests` rule gives admins full read/write always, and gives every other active role exactly one thing: flipping `status` `Expected`/`Arrived` -> `Arrived`/`Departed` while every other field (`name`/`category`/`hostName`/`purpose`/`validFrom`/`validUntil`/`createdBy`) stays byte-for-byte the same - a guard can never create, delete, cancel, or edit a guest's core details, only advance it through the gate. Walk-in (non-VIP) visitor passes get the same one-way self-service return: `rfidUsers/{id}/status`'s `.validate` now also allows any active role to set it to `Inactive` (never back to `Active`) when the record's own `role` is `Visitor`, so a guard can return a pass from the Dashboard's `VisitorPassesPanel` (`setRfidUserStatus`, already existed) without admin help. `useVisitorPasses` excludes any `rfidId` that an `expectedGuests` entry claims, so a checked-in VIP's pass shows only in `GuestClearancePanel`, never doubled up in `VisitorPassesPanel`. Both Dashboard panels render nothing when there's nothing to act on (no empty-table clutter). No new CSS - both panels and both new modals (`AddExpectedGuestModal`, `CheckInGuestModal`) reuse `.activity-panel`/`.activity-table`/`.registration-form`/`.rfid-scan-row` etc. **This phase's `expectedGuests` rule must be deployed** (`firebase deploy --only database`, same deploy as Phase 10) before pre-clearance works at all.

**Styling**: one global stylesheet, `src/index.css` (~1900 lines), using plain class names (no CSS modules/Tailwind/styled-components). Match existing class-naming conventions (e.g. `dashboard-*`, `payment-*`, `activity-*`) when styling new UI rather than introducing a new styling approach.

## Known issues to be aware of

**Sign-up, email verification & admin approval** (`/signup` → `SignupForm.jsx`, `/pending` → `PendingApprovalPage.jsx`, both public routes; `signUp()`/`refreshEmailVerified()`/`resendVerificationEmail()` in `src/services/auth.js`): a signup picks a role from a dropdown but that is only a **request**. `signUp()` creates the Auth account and writes `adminProfiles/{uid}` with `status: 'Pending'`, the harmless interim `role: DEFAULT_SIGNUP_ROLE` (`Security Guard`), the picked role in `requestedRole`, and `emailVerified: false`, then calls `sendEmailVerification` (Firebase's default email, which contains the verify link). `RequireAuth` redirects any `Pending`/`Inactive` profile (`status` from `useAuth()`) to `/pending`, which shows the two steps (verify email via `useEmailVerification`, then wait for an admin) and flips to the dashboard automatically once status becomes `Active`. `Inactive` is also how a declined request is stored. Approvals live in `PendingApprovalsPanel.jsx` (top of Account Management): each row shows the **requested role** and whether the email is verified; Approve is disabled until the email is verified, and `canApproveRole()` (`src/constants/roles.js`) limits an Administrator to approving `Security Guard` requests while a Super Admin can approve any. Approve = targeted `update({ role: requestedRole, status: 'Active' })`, never a full `set()`. Deactivating/reactivating an existing staff account is a Super-Admin-only Deactivate/Reactivate button in Account Management's Staff Accounts table (`setAdminStatus`, same targeted-update pattern; you can't deactivate yourself): `Inactive` locks the account out of every database path via the rules and bounces it to `/pending`, but does not disable the Firebase Auth login itself.

`database.rules.json` is the real enforcement, not the UI: (1) every non-`adminProfiles` node now requires the caller's own `adminProfiles/{uid}/status === 'Active'` (so Pending/declined accounts — and Auth accounts with no profile at all — can read/write nothing); (2) a user can only create their *own* profile as `status: 'Pending'` with `role: 'Security Guard'`, and can never change their own `role`/`status`/`requestedRole`; (3) Pending → Active requires `emailVerified === true`, and `emailVerified` can only be set to `true` by the profile's owner while their auth token says `email_verified` (the client force-refreshes the ID token first); (4) Administrators can read *only* the `status == 'Pending'` query of `adminProfiles` and write only Pending records, only approving `Security Guard` requests; Super Admins can do everything. Consequences: the first Super Admin/Administrators must still be provisioned in the Firebase console **with `status: 'Active'`** on their `adminProfiles/{uid}` record (an existing profile without it is locked out of everything once these rules are deployed); the old self-toggle on My Profile's status pill was removed (status is admin-controlled now); and `storage.rules` was **not** tightened to match — Storage can't read RTDB, so a Pending account could still upload to `vehicle-snapshots/` until that's addressed. Deploy with `firebase deploy --only database`.

**Recovering from a bad signup** (e.g. a mistyped email that can never verify): `/pending` has a password-confirmed "Cancel signup & start over" (`CancelSignupModal`, `useCancelSignup` -> `reauthenticate` + `deleteOwnAccount` in `services/auth.js`) that deletes the user's own `adminProfiles/{uid}` and Firebase Auth login so the email can be reused; it's available to Pending and Inactive accounts (so a deactivated staff member could delete their own record too - accepted). A Super Admin can also **Remove** an Inactive profile from Account Management's Staff Accounts table (`deleteAdminProfile`); that deletes only the RTDB record, since a client can't delete another user's Auth login - the removed user, on next sign-in, lands on `/pending` as "Account removed" (`RequireAuth` now sends a profile-less login, `status` null, there instead of letting it through) and can use "Start over" to clear their login. No rules changes: `adminProfiles/{uid}` `.write` already allows the owner or a Super Admin, and deletes skip `.validate`.

Assigning a *different* user's role (e.g. a Super Admin promoting a Security Guard to Administrator) has no UI anywhere in the app — `database.rules.json` only allows a user to write their own `adminProfiles/{uid}`, and only when their own current role is already `Super Admin` (or the profile doesn't exist yet and the role being set is `Security Guard` — the self-signup path). Cross-user role assignment today means editing `adminProfiles/{otherUid}/role` directly in the Firebase console. Building an in-app user-management screen for this is a natural next step but out of scope until asked for.

Because `System Settings` is now Super-Admin/Administrator-only (`ADMIN_ROLES` in `src/constants/roles.js`), and "My Profile" / "Change Password" are only linked to from `SettingsPage`, a Security Guard currently has no in-app way to reach `/profile` or open `ChangePasswordModal` even though the `/profile` route itself has no role restriction. If this needs fixing, it means adding a role-independent entry point to those (e.g. in `AppShell` or the top bar), not loosening the `/settings` guard.

`ChangePasswordModal` (`src/components/modals/ChangePasswordModal.jsx`) reauthenticates with the current password via `reauthenticateWithCredential`/`EmailAuthProvider` before calling `updatePassword` — both from `firebase/auth`, using `auth.currentUser`. It shows a friendly error if there's no real signed-in user (this used to matter for the login bypass; the bypass has since been removed, so `auth.currentUser` should always be real now for anyone who successfully reaches an authenticated route).
